# SEO Rules for Portfolio Website

Этот файл обязателен для любого AI-ассистента или разработчика, который создаёт или изменяет страницы сайта. SEO должно проверяться вместе с дизайном, контентом и адаптивностью, а не откладываться до конца проекта.

Проект является портфолио графического и multidisciplinary-дизайнера. Здесь нет блога, категорий, тегов и архивов. Главные цели SEO: понятная профессиональная специализация, корректное представление проектов, локальная и международная видимость, переход к контактам.

## 1. Title и meta description

- У каждой индексируемой страницы должны быть уникальные `title` и `meta description`.
- Рекомендуемый формат главной: `Vladimir Potapov | Visual Designer | Prague & Remote`.
- Для проекта: `[Project name] | Vladimir Potapov`.
- Для раздела экспертизы: `[Expertise] | Vladimir Potapov`.
- `title` желательно удерживать в пределах 50-60 символов. Ясность важнее механического соблюдения лимита.
- `meta description` желательно удерживать в пределах 140-155 символов.
- Description должен кратко объяснять содержание страницы и давать понятную причину открыть её или связаться с дизайнером.
- Не повторять один и тот же description на всех страницах.
- Не добавлять устаревший `<meta name="keywords">`: поисковые системы практически не используют его для ранжирования.
- Фразы `visual designer`, `graphic designer`, `brand identity`, `marketing design`, `3D visualization`, `Prague`, `remote` применять только там, где они естественно соответствуют странице.

## 2. URL и индексируемая структура

- Использовать короткие URL в lowercase: `/projects`, `/about`, `/contact`.
- Проекты: `/projects/[project-slug]`.
- Экспертиза: `/expertise/[expertise-slug]`.
- Slug должен быть понятным и постоянным; не включать даты без необходимости.
- Не создавать категории, теги и архивы дат.
- При изменении URL обязательно предусмотреть redirect со старого адреса.
- У каждой страницы должен быть корректный canonical URL на production-домене.
- Страница 404 не должна индексироваться.

## 3. Заголовки и содержание

- На каждой странице должен быть ровно один содержательный `h1`.
- `h1` должен описывать конкретную страницу. Имя дизайнера и специализация должны естественно присутствовать на главной или в ближайшем доступном тексте.
- `h2` и `h3` использовать по логической иерархии секций, не ради размера шрифта.
- Не пропускать уровни заголовков без причины.
- В тексте не должно быть Lorem Ipsum, технических заглушек и выдуманных результатов проекта.
- Тексты должны быть краткими, профессиональными и написанными для людей. Не повторять ключевую фразу искусственно.
- У каждой страницы проекта должны быть понятны название, роль, год, задачи, вклад и результат, если эти данные доступны.
- Ссылки должны иметь осмысленный текст или доступное имя; избегать неопределённых подписей вроде `Click here`.

## 4. Изображения и видео

- Содержательные изображения получают краткий описательный `alt`, соответствующий их роли на странице.
- Не перегружать `alt` ключевыми словами и не начинать его словами `image of` или `photo of`.
- Декоративные изображения получают `alt=""`; это правильное исключение, а не ошибка.
- Если несколько изображений показывают один кейс, описывать конкретное содержимое каждого, а не повторять один alt.
- Для изображений указывать стабильные размеры или `aspect-ratio`, чтобы снизить layout shift.
- Изображения ниже первого экрана загружать лениво. Hero и вероятный LCP-элемент не должны получать `loading="lazy"`.
- Использовать сжатые современные форматы, сохраняя качество дизайна.
- Видео должны иметь poster, подходящий preload и не блокировать первоначальную загрузку страницы.

## 5. Open Graph и социальные превью

- У каждой важной страницы должны быть `og:title`, `og:description`, `og:url`, `og:type` и `og:image`.
- Главная использует общий портретный OG-баннер.
- Страница проекта использует собственное главное изображение проекта.
- Рекомендуемый размер OG-изображения: `1200 x 630 px`, JPG или PNG разумного веса.
- Добавлять Twitter Card как `summary_large_image`.
- Все OG URL должны быть абсолютными и использовать production-домен.

## 6. Structured data

- На главной использовать JSON-LD типа `Person`.
- Минимальные поля: `name`, `jobTitle`, `url`, `image`, `sameAs`.
- При наличии можно добавить `address` с городом и страной, `knowsAbout` и контактные данные, которые уже публично показаны на сайте.
- `sameAs` должен содержать только реальные публичные профили.
- Не использовать `LocalBusiness`, пока сайт не представляет зарегистрированный бизнес с достоверным адресом и бизнес-данными.
- Для страниц проектов допустим `CreativeWork` или `VisualArtwork`, если данные заполнены корректно. Не добавлять schema только ради количества разметки.

## 7. Техническое SEO

- Сайт должен иметь корректные `robots.txt` и `sitemap.xml` для production-домена.
- HTML должен содержать правильный `lang`; после появления русской версии использовать отдельные URL и `hreflang`.
- Все страницы должны быть доступны обычными ссылками `<a href>` без зависимости от JavaScript.
- Page transition не должен мешать кнопкам Back/Forward, deep links, якорям или индексации.
- Не допускать битых ссылок, отсутствующих ассетов, горизонтального скролла и контента, доступного только при hover.
- Важный текст должен присутствовать в HTML, а не быть отрисован только canvas или изображением.
- Сохранять доступный focus state и навигацию с клавиатуры.

## 8. Скорость и Core Web Vitals

- Приоритет: отсутствие layout shift, быстрый первый экран и отзывчивые взаимодействия.
- Не загружать тяжёлые изображения и видео до необходимости.
- Не добавлять библиотеку, если задача надёжно решается существующим кодом проекта.
- Анимации должны использовать производительные свойства и уважать `prefers-reduced-motion`.
- После значимых изменений проверять desktop и mobile, особенно Android Chrome и Safari/iOS.

## 9. Локальное и международное позиционирование

- Упоминать Prague / Czech Republic только в естественных местах: title или description главной, About, Contact и structured data.
- Если работа доступна удалённо, использовать формулировку `Prague & Remote` или естественный эквивалент в тексте.
- Не создавать искусственные страницы под города и услуги без уникального полезного содержания.

## 10. Проверка при создании или изменении страницы

Перед завершением задачи проверить:

1. Есть ли один корректный `h1` и логичная иерархия `h2-h3`.
2. Уникальны ли `title` и `meta description`.
3. Корректны ли canonical, Open Graph и OG image.
4. Есть ли осмысленные alt у содержательных изображений и пустые alt у декоративных.
5. Работают ли внутренние ссылки и адрес страницы.
6. Нет ли placeholder-контента, битых ассетов и горизонтального скролла.
7. Не ухудшилась ли мобильная версия и скорость загрузки.
8. Нужно ли обновить `README.md`, `PROJECT_CONTEXT.md` и этот файл.

## 11. Приоритет правил

- Не менять утверждённый дизайн только ради буквального добавления ключевой фразы.
- Не обещать услуги, опыт, награды или локацию, которых нет в подтверждённом контенте.
- Сначала точность и понятность, затем SEO-формулировки.
- При конфликте между конверсией, доступностью и поисковой оптимизацией выбирать ясный и доступный пользовательский опыт.
